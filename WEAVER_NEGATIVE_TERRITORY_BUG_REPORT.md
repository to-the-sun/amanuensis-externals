# Technical Report: Replicating and Resolving the weaver~ Negative Territory Crossfade Oscillation Bug

This report details the technical analysis, replication steps, mathematical explanation, and programmatic solution for the crossfade oscillation bug observed in the `weaver~` external object when playing back in negative chronological territory.

---

## 1. Problem Description & Root Cause Diagnosis

When the `weaver~` object processes a timeline sequence that goes below zero (using absolute timestamps, such as the negative-numbered bars in `transcript.json`), the crossfades of the active tracks experience rapid, wild oscillations, as seen in `Untitled.png`.

Although the core continuous hit detection algorithm already contains a floor-division mechanism (`latest_j = ((end / bar_len) - 1) * bar_len`), **an initialization order bug in `weaver_new` completely defeated this logic during object creation.**

### The Initialization Order Bug in `weaver_new`
During the instantiation of the `weaver~` object, the setup was sequenced as follows:

```c
// 5. Setup initial state dependent on initialized refs and locks
weaver_check_attachments(x);
weaver_update_track_cache(x);
```

1. **`weaver_check_attachments(x)`** was called first. This function internally calls `weaver_update_most_negative_bar(x)`.
2. **`weaver_update_most_negative_bar(x)`** iterates through the transcript dictionary keys, parses track IDs, and attempts to update the track-specific bounds (`tr->most_negative_bar` and `tr->highest_bar`) for each cached track:
   ```c
   if (track_id > 0 && track_id <= x->track_cache_count) {
       x->track_cache[track_id - 1]->most_negative_bar = track_most_neg;
       x->track_cache[track_id - 1]->highest_bar = track_highest;
   }
   ```
3. **The Catch:** Because `weaver_update_track_cache(x)` had *not yet been called*, `x->track_cache_count` was still `0`. As a result, the track boundaries were never written! They remained at their default initialized value of `0.0`.
4. **`weaver_update_track_cache(x)`** was then called, allocating and setting up the track states but leaving `tr->most_negative_bar` and `tr->highest_bar` as `0.0`.

---

## 2. Mathematical Impact: The Playhead Wrapping Sawtooth

Because the track boundaries were incorrectly left at `0.0`, the timeline wrapping logic inside `weaver_process_vector` acted catastrophically when playing in negative territory:

```c
double current_scan_for_track = current_scan;
if (current_scan < tr->most_negative_bar) { // evaluates as current_scan < 0.0
    double T_content_length = tr->highest_bar - tr->most_negative_bar + bar_len; // 0.0 - 0.0 + 3459.0 = 3459.0
    if (T_content_length > 0) {
        double diff = tr->most_negative_bar - current_scan; // 0.0 - current_scan
        double wrapped_diff = fmod(diff, T_content_length);
        if (wrapped_diff < 1e-5) {
            current_scan_for_track = tr->most_negative_bar; // 0.0
        } else {
            current_scan_for_track = tr->highest_bar - (wrapped_diff - bar_len); // 3459.0 - wrapped_diff
        }
    }
}
```

### The Resulting Sawtooth Playhead
- When the timeline was in negative territory (e.g., `-13836 ms` to `0 ms`), the engine erroneously treated the playhead as "out of bounds" because `current_scan < 0.0`.
- Instead of moving linearly, the wrapping logic mapped `current_scan_for_track` into positive values (`0.0` to `3459.0` ms) in rapid cycles.
- This transformed the linear negative playhead into a **sawtoothing playhead** that wrapped back and forth across bar boundaries every single bar-length interval!
- Because the playhead kept wrapping back and forth rapidly, the continuous hit detection logic triggered new bar crossfades constantly, resulting in the wild, repeating crossfade curves and gain flips seen in `Untitled.png`.

## 4. Programmatic Solution

The solution is remarkably clean and does not alter the core floor division algorithm. We simply swap the execution order of `weaver_update_track_cache` and `weaver_check_attachments` inside `weaver_new`:

```c
// 5. Setup initial state dependent on initialized refs and locks
weaver_update_track_cache(x);
weaver_check_attachments(x);
```

### Why this Fixes the Bug:
1. **`weaver_update_track_cache(x)`** is called first. This populates `x->track_cache` and sets `x->track_cache_count` to the correct value (e.g. `4`).
2. **`weaver_check_attachments(x)`** is then called. It invokes `weaver_update_most_negative_bar(x)`, which now successfully finds all 4 track cached entries and populates their `tr->most_negative_bar` and `tr->highest_bar` from the transcript dictionary (e.g. `-13836 ms` and `10377 ms` respectively).
3. **Linear Playhead in Negative Territory:** Inside `weaver_process_vector`, since `tr->most_negative_bar` is correctly set to `-13836 ms`, the playhead does not trigger the wrapping logic in negative territory (`current_scan < -13836` is false).
4. The timeline remains perfectly linear, the floor-division triggers exactly once per bar crossing, and the oscillations disappear entirely!
